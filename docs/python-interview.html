数据类型与可变性 · Types & Mutability

Q. 可变 vs 不可变？ / Mutable vs immutable

不可变 immutable: int, float, bool, str, tuple, frozenset, bytes。可变 mutable: list, dict, set, bytearray 及大多数自定义对象。

意义：不可变对象可哈希 (hashable)，能做 dict 键 / set 元素；作为函数参数更安全。可变对象作默认参数或类属性会有共享陷阱（见 陷阱题）。

Q. list vs tuple？何时用哪个？

list 可变、用于同类元素的集合；tuple 不可变、更省内存、可作字典键、常表达"固定字段的记录"。经验法则：异构且固定 → tuple；同构且会变 → list。

Q. 深拷贝 vs 浅拷贝？ / Deep vs shallow copy

浅拷贝 (shallow)：list(x) / x[:] / copy.copy 只复制最外层，内部嵌套对象仍共享引用。深拷贝 (deep)：copy.deepcopy 递归复制所有层级。

函数 · 装饰器 · 生成器 · Functions, Decorators & Generators

Q. 什么是闭包？作用域规则 LEGB？ / Closures & scope

闭包 (closure)：内层函数捕获并"记住"外层作用域的变量，即使外层已返回。名字解析遵循 LEGB：Local → Enclosing → Global → Built-in。修改外层变量用 nonlocal，修改全局用 global。

Q. 装饰器是什么？ / What is a decorator?

装饰器本质是接收函数、返回新函数的高阶函数，用来在不改原函数代码的前提下增加行为（日志、计时、缓存、鉴权）。用 functools.wraps 保留原函数的名字/文档。

🗣️ Say it in English — decorators

“A decorator is a higher-order function that takes a function and returns a new function wrapping it, so I can add behavior — logging, timing, caching, auth — without touching the original code. I always use functools.wraps so the wrapper keeps the original function's name and docstring. Under the hood, @decorator is just func = decorator(func).”

Q. 生成器 vs 普通函数？yield 有什么用？ / Generators

含 yield 的函数是生成器 (generator)：调用时不立即执行，返回一个惰性 (lazy) 迭代器，每次 next() 执行到下一个 yield 并暂停、保留状态。好处是常数内存处理大/无限数据流，而不是一次性构建整个列表。

Q. 迭代器 (iterator) vs 可迭代对象 (iterable)？

iterable 实现 __iter__（能被 for 遍历，如 list/dict/str）；iterator 额外实现 __next__ 且是一次性的（如生成器、iter(list) 的结果）。for 循环先对 iterable 调 iter() 拿到 iterator，再反复 next() 直到 StopIteration。

Q. 上下文管理器与 with？ / Context managers

with 语句用上下文管理器保证资源被正确获取和释放（文件、锁、连接），即使发生异常也会执行清理。实现 __enter__ / __exit__，或用 @contextlib.contextmanager 装饰生成器。

面向对象 · MRO · 魔术方法 · OOP, MRO & Dunder Methods

Q. 类属性 vs 实例属性？__slots__？

类属性被所有实例共享；实例属性存于每个对象的 __dict__。定义 __slots__ 可取消 __dict__、省内存并加速属性访问，代价是不能动态加属性——适合大量小对象。

Q. super() 与 MRO？菱形继承怎么解析？ / Method Resolution Order

MRO (Method Resolution Order) 决定多继承时方法查找顺序，CPython 用 C3 线性化算法，保证一致且单调。super() 按 MRO 找"下一个"类，而非字面意义的父类——这正是菱形继承 (diamond) 下每个基类只被调用一次的关键。用 Cls.__mro__ 查看顺序。

C3 线性化：MRO 到底怎么算出来的

C3 的目标是同时满足三条：子类排在父类前面；多个父类之间保留声明顺序；每个类只出现一次。公式是 L[D] = D + merge(L[B], L[C], [B, C])——merge 每次从各列表表头挑一个候选，条件是这个类不能出现在任何其他列表的非表头位置（即不能还是别人的祖先），选中就从所有列表里删掉它，重复直到取完。

⚠️ 常见误区：以为 super() 是"调用父类"

super() 找的不是字面意义上的父类，而是 MRO 链上当前类的下一个。B.go 里的 super() 解析到的是 C（MRO 里排在 B 后面的那个），不是 A；C.go 里的 super() 才轮到 A。如果把它换成硬编码的 A.go(self)，B 和 C 就会各自独立调一次 A，A 被执行两次——这是面试里最常见的追问陷阱。

⚠️ MRO 冲突会直接报错，不是"随便选一个顺序"

如果两个类以互相矛盾的顺序声明基类，C3 算法找不出一个能同时满足两边约束的线性顺序，Python 会在类定义时直接抛错，而不是悄悄选一个顺序运行。

💡 比方法覆盖更常踩的坑：__init__ 链式调用

多继承下 __init__ 同样要靠 super().__init__(**kwargs) 沿 MRO 传递。只要有一环忘了调 super().__init__()，或者干脆写成硬编码的 Base.__init__(self)，链条就在那一环断掉——后面基类的初始化会被直接跳过，往往在运行很久后才因为某个属性没初始化而报错，比方法覆盖问题更隐蔽。

🗣️ Say it in English — diamond inheritance & MRO

“Python resolves multiple inheritance with C3 linearization: it builds an order where every subclass comes before its parents, sibling classes keep their declared order, and each class appears exactly once. The formula is roughly L[D] = D + merge(L[B], L[C], [B, C]) — at each step you take the head of a list only if it doesn't appear in the tail of any other list, which is what prevents a shared ancestor from being picked too early.”

“The part people get wrong is thinking super() calls 'the parent class.' It actually calls whatever comes next in the MRO for the current class, which is why each class in a diamond only runs once — if you hardcode the parent instead of using super(), the shared base class gets called twice. The same rule applies to __init__: if one class in the chain skips super().__init__(), everything after it in the MRO silently never gets initialized.”

Q. @staticmethod vs @classmethod vs 实例方法？

实例方法收 self（操作实例）；@classmethod 收 cls（操作类，常用作替代构造器如 from_json）；@staticmethod 不收 self/cls（只是放在类命名空间里的普通函数）。@property 把方法伪装成属性访问。

@classmethod vs @staticmethod：继承时的关键差异。唯一本质区别是——classmethod 自动收到 cls（实际调用的那个类），staticmethod 什么都不收、只能硬编码类名。两个方法干"同一件事"，结果却分道扬镳：

Child.via_cls() 里 cls 就是 Child，于是拿到 Child.name；而 staticmethod 拿不到类，只能写死 Base，子类一调就错。这正是为什么替代构造器 / 工厂方法必须用 classmethod——return cls(...) 才能让子类返回子类实例，天然支持多态。

👑 判断标准 · Which one?

问自己："这个方法需要引用类吗？" 需要（cls(...) 构造、读写类属性、按子类分派）→ @classmethod；self 和 cls 都不用（纯工具/校验函数）→ @staticmethod（甚至可以直接做成模块级函数）。

Q. __eq__ 与 __hash__ 的联动规则？（高频！）

若重写 __eq__，对象默认变得不可哈希（__hash__ 被设为 None），因为"相等的对象必须有相同 hash"这个约束不再自动成立。若要放进 set/dict，需同时正确实现 __hash__。@dataclass(frozen=True) 会自动帮你生成二者。

Q. 常用魔术方法 (dunder) 有哪些？

__init__(初始化) / __new__(创建实例) / __repr__(调试字符串) / __str__(可读字符串) / __eq__ / __hash__ / __len__ / __getitem__(下标) / __iter__ / __call__(像函数一样调用) / __enter__+__exit__(with)。dataclass、namedtuple、Enum 能自动生成很多样板代码。

Q. 什么是元类 (metaclass)？__new__ 何时触发？

元类是"类的类"——普通对象由类创建，而类本身由元类创建，默认元类是 type。自定义元类可以在类定义时介入类的创建（注册、日志、注入方法、统一校验）。元类的 __new__(mcls, name, bases, namespace) 在定义类的那一刻被调用（不是创建实例时）：name 是类名字符串，bases 是基类元组，namespace 是类体字典。而且元类会被继承，子类不写 metaclass= 也沿用。

💡 面试要点

类只被创建一次，所以元类 __new__ 只在定义时跑一次；记住 type(obj) 是它的类，type(类) 是它的元类。实践中元类很少用——能用类装饰器或 __init_subclass__ 钩子解决的就别上元类。

🗣️ Say it in English — threads vs async vs processes

“I pick based on the workload. For I/O-bound work with lots of waiting, threads or asyncio work well — the GIL is released during I/O. Asyncio scales to thousands of concurrent connections in a single thread with no context-switch overhead, as long as I avoid blocking calls. For CPU-bound work I use multiprocessing to get true parallelism across cores, since each process has its own GIL. The trade-off with processes is higher memory overhead and needing to pickle data between them.”

asyncio 核心机制 · Asyncio Internals

Staff 级别面试不会只问"async 是什么"，而是问调度模型、任务生命周期、取消与异常怎么传。下面按面试官的追问顺序展开。

1. 事件循环心智模型 · The event loop in one picture

一个线程 + 一个就绪队列。循环反复做三件事：

  • ① 从就绪队列取出一个任务，执行它的 Python 代码；
  • ② 任务跑到 await 且需要等 IO 时，登记回调后挂起自己，把控制权交回循环；
  • ③ 操作系统通知 IO 就绪（epoll/kqueue），循环把对应任务重新放回就绪队列。
🔑 一句话

并发 ≠ 并行。任意时刻只有一段 Python 字节码在跑；asyncio 快，是因为把"等待"重叠了，而不是因为算得更快。所以它对 IO 密集有效，对 CPU 密集零收益。

🔁 事件循环三步循环 · The event loop cycle
任意时刻只有一段字节码在跑；asyncio 快是因为把"等待"重叠了，而不是算得更快。

⚠️ 最容易答错的一点

await f() 是顺序执行——等它做完才往下走，没有任何并发。并发的起点是 create_task（或 gather / TaskGroup），它先把所有协程塞进循环，再统一等结果。

⏱ 顺序 vs 并发：同样两个 work(1)，耗时差一倍
await 是顺序执行；并发的起点是 create_task —— 先把协程都塞进循环，再统一等结果。

4. 取消与异常传播 · Cancellation & error propagation

要点说明
task.cancel() 不是立刻杀死它只是请求取消：在任务的下一个 await 点抛出 CancelledError。纯 CPU 循环里没有 await，取消不了。
CancelledError 继承 BaseExceptionPython 3.8+ 起如此，所以 except Exception 抓不到它——这是故意设计，防止业务代码误吞取消信号。
清理放 finally取消发生时 finally 仍会执行。若清理本身要 await，注意别在取消期间再被取消；必要时用 asyncio.shield() 保护关键收尾。
⚠️ Task 会被 GC 掉事件循环只持弱引用。asyncio.create_task(f()) 不保存返回值，任务可能被垃圾回收而中途消失、异常静默丢失。务必存起来（放 set 里 + add_done_callback(discard)），或用 TaskGroup。
孤儿异常任务抛异常但从没被 await/取结果 → 只在 GC 时打印 "Task exception was never retrieved"。

5. 头号杀手：阻塞调用 · Never block the loop

事件循环是单线程。任何同步阻塞——time.sleep()、requests.get()、大文件读写、重 CPU 计算、同步的 DB driver——都会让所有协程一起卡住。

症状解法
阻塞 IO（同步库、文件、老 SDK）await asyncio.to_thread(fn, *args)3.9+ 或 await loop.run_in_executor(pool, fn)——丢到线程池，GIL 在 IO 时会释放
CPU 密集（解析、加密、向量运算）run_in_executor(ProcessPoolExecutor(), ...)，真并行绕开 GIL
不知道谁在卡asyncio.run(main(), debug=True) 会对 >100ms 的回调发出告警；loop.slow_callback_duration 可调

6. 同步原语与队列 · Locks & Queues

用 asyncio.Lock/Event/Queue，不要用 threading 版本——后者会阻塞整个循环。asyncio 的锁保护的是"跨 await 的临界区"（同一线程内，没 await 就不会被打断）。

7. 高频陷阱速查 · Async gotchas

写法问题
result = fetch(url)忘了 await：拿到的是 coroutine 对象，不是结果；warning 提示 "never awaited"
time.sleep(1) 写在 async def 里阻塞整个循环，应为 await asyncio.sleep(1)

🗣️ Say it in English — how asyncio actually works

“Asyncio is cooperative concurrency on a single thread. The event loop keeps a queue of ready tasks; when a coroutine hits an await on I/O, it registers a callback and yields control back to the loop, so the loop can run something else while the socket is waiting. Nothing is preempted — a task only gives up control at an await point, which is why one blocking call stalls everything.”

“The distinction I'd stress is coroutine versus task. Calling an async function just builds a coroutine object; it doesn't run. await-ing it runs it sequentially. Concurrency starts when you wrap it in a task — with create_task, gather, or ideally a TaskGroup, which gives structured concurrency: if one child fails, its siblings get cancelled and you get an ExceptionGroup, instead of orphaned tasks leaking in the background.”

限流三件套 · Semaphore / AsyncLimiter / ClientSession

批量调 LLM API、批量抓取——这是 asyncio 最常被拿来考的落地场景。三个组件各管一件事，缺一个就会出事：并发打爆下游、被 429 限流、或者把连接池耗尽。

标准骨架 · The canonical skeleton

🔑 一句话记住分工

Semaphore 管"存量"（同时有几个在跑）· AsyncLimiter 管"流量"（单位时间发起几个）· ClientSession 管"资源"（TCP 连接复用）。

🚦 三道门：一个请求怎么从队列流到下游
Semaphore 管"存量" · AsyncLimiter 管"流量" · ClientSession 管"资源"——缺一个就会出事：并发打爆下游、被 429 限流、或连接池耗尽。

Semaphore vs AsyncLimiter：本质区别在"谁归还额度"

asyncio.Semaphore(10)AsyncLimiter(50, 60)
限制的量存量：任一时刻在飞的请求数 ≤ 10流量：任意 60 秒窗口内发起数 ≤ 50
额度怎么回来请求结束时归还 → 依赖下游快慢，是闭环反馈时间自动补充（漏桶/令牌桶）→ 与请求是否完成无关
下游变慢时自动降速（槽位不释放）✅照样按点发 → 在飞数量堆积 ❌
请求很快时不设防，可能瞬间打出上千个 ❌稳稳压住速率 ✅
对应的下游限制连接数 / 并发配额 / 内存RPM、TPM、QPS 配额（LLM API 的典型形态）
💡 为什么两个都要

只有 Semaphore：请求平均 50ms 就返回时，10 个槽位一秒能转 200 轮 → 轻松超 RPM 被 429。
只有 AsyncLimiter：下游卡到 30s 不返回时，限流器照发不误 → 在飞请求无限堆积，内存和连接池双爆。
一个防"太快"，一个防"太多"，正交。

嵌套顺序：为什么 limiter 在外、sem 在内

当前写法 limiter → sem → 请求：协程先排队等"发令枪"，拿到令牌后再抢并发槽。反过来（sem 在外）会怎样？

  • sem 在外：协程先占住并发槽，然后卡在限流器上干等。槽位被"排队中"的协程占着，而它们其实什么都没做 → 有效并发下降，Semaphore 形同虚设。
  • limiter 在外（推荐）：等待发生在占资源之前，槽位只被真正在发请求的协程持有。
💡 通用原则

"先等时间，再占资源"——所有纯等待型的门（限流、退避）放外层，所有持有稀缺资源的门（并发槽、连接、锁）放内层，且持有时间越短越好。

aiohttp.ClientSession：为什么必须"建一次，全程共享"

它内部是什么每次新建的代价
一个 TCPConnector 连接池（默认 limit=100 总连接、limit_per_host=0 不限）+ cookie jar + 默认 headers + DNS 缓存每个请求都要重做 DNS 解析 → TCP 三次握手 → TLS 握手，延迟涨几十到几百毫秒；连接无法复用（没有 keep-alive）；还会漏 socket 和 "Unclosed client session" 警告
⚠️ 隐形的第四道门

ClientSession 的连接池本身就是一个限流器。如果 Semaphore(200) 但连接池 limit=100，实际并发被压到 100，多出来的协程在池里排队——调并发时两个数要一起看，否则会以为限流没生效。

快问快答 · Rapid fire

问答
Semaphore 用 threading 的行不行？不行。threading.Semaphore.acquire() 是阻塞调用，会卡死整个事件循环。必须用 asyncio.Semaphore（它不是线程安全的，但单线程里不需要）。
为什么不用 time.sleep 做限流？同理，阻塞循环。限流器内部用的是 await asyncio.sleep。
AsyncLimiter 是令牌桶还是漏桶？aiolimiter 实现的是漏桶语义：容量 max_rate，按 max_rate/time_period 的速率持续补充，允许突发到桶容量。
三个门都是 async with，凭什么？它们都实现了 __aenter__/__aexit__。async with 的价值是异常安全——请求抛错时槽位/连接照样归还，用 try/finally 手写等价但容易漏。
怎么定 Semaphore 的值？从下游文档的并发配额或 限流QPS × 平均延迟（Little's Law）估一个起点，再用 429 率和 p99 延迟压测调整。
多进程/多实例部署怎么办？这套限流是单进程内存态的。多副本要么把额度按副本数均分，要么上 Redis 做分布式令牌桶。
🗣️ Say it in English — rate limiting a batch of API calls

“I'd layer three things. A semaphore caps how many requests are in flight at once — it protects my own memory and the connection pool, and it self-throttles when the upstream slows down, because slots only free up on completion. A rate limiter caps how many I start per minute — that's what maps to an API's RPM quota, and it's replenished by time, not by completion. And a single shared ClientSession keeps a connection pool alive so I'm not paying for a TCP and TLS handshake on every call.”

“Order matters: the rate limiter goes on the outside and the semaphore inside, so a coroutine waits for its turn before it occupies a concurrency slot. Otherwise idle waiters hold slots and my effective concurrency silently drops. On top of that, production code needs exponential backoff with jitter on 429s — honoring Retry-After — and for LLM APIs specifically I'd meter tokens as well as requests, since providers limit TPM and RPM independently.”

lambda 什么时候需要 x=x？延迟绑定 vs 立即绑定 · When lambdas need the default-arg snapshot

判断标准就两条，两条都满足才需要 x=x 这个默认参数技巧： ① lambda 里用到的变量是从外层作用域捕获的自由变量（不是它自己的形参）；② 这个 lambda 会活到外层变量已经改变之后才被调用（存起来、事后才用）。只要少一条，就不需要。

① 当 lambda 作为参数、立刻被调用（sort/map/filter 的 key/func）：不需要

② lambda 捕获了外层变量，但在同一轮循环里立刻被使用：不需要

③ 把 lambda 存起来，留到循环结束后才调用：需要

为什么会这样：闭包捕获的是变量本身（一个 cell），值在调用时才去查找，而不是定义时就固定——这就是延迟绑定 (late binding)。Python 循环也不为每轮迭代新建作用域，i 全程是外层同一个变量，每轮只是重新绑定它，所有闭包共享同一个 cell：

④ 辨析：lambda i: i 不等于 lambda i=i: i，一个 = 号完全改变行为

写法i 从哪来funcs[k]()（不传参）调用结果
lambda: i捕获外层自由变量（闭包）循环内立刻用没事；存起来事后调 → 全部是最后一轮的值（延迟绑定陷阱）
lambda i: i自己的形参，同名遮蔽外层变量，不构成闭包捕获直接报 TypeError（缺少参数）；传参就原样返回传入值——和外层循环毫无关系
lambda i=i: i自己的形参，但默认值在定义时求值，读取的是当前那一轮的外层 i[0, 1, 2]——提前绑定，标准修复写法
👑 一句话记住

lambda i: i 里的 i 每次调用都要由外部传入，跟循环无关；lambda i=i: i 里的 i 在定义那一刻就已经确定，之后调用可以不传参直接拿到当轮的值。少一个 =，是"要求传参的形参"和"定义时拍好快照的默认值"两种完全不同的语义。

🗣️ Say it in English

“Whether a lambda needs the x=x default-argument trick comes down to two questions: is the variable a free variable captured from an enclosing scope rather than the lambda's own parameter, and will this lambda outlive the current loop iteration before it's called? If both are true — like storing callbacks in a loop — Python's late binding means every closure reads the same shared cell, so they all end up seeing the final value. A default argument snapshots the value at definition time instead, which is early binding. But if the lambda is invoked immediately, like a sort key or a map function, there's no capture at all — the variable is just the lambda's own parameter, supplied fresh on every call, so the trick isn't needed.”

👑 为什么"多趟"能行：稳定排序

Python 的 sort/sorted 是稳定的 (stable, Timsort)：值相等的元素保持原有相对顺序。所以后一趟按主键排时，主键相同的元素会保留前一趟按次键排好的顺序——因此次要键先排、主要键后排。稳定性也意味着：只给一个 key 时，并列元素保持输入原序。

高频陷阱题 · Classic Gotchas

面试官爱用这些考你对语言的真正理解。看到就要能立刻说出"为什么"。

1. 可变默认参数 · Mutable default argument

默认值在函数定义时只创建一次，被所有调用共享——用 None 作哨兵修复。

2. 遍历时修改列表 · Mutating a list while iterating

会跳过元素或索引错乱。应遍历副本 (for x in lst[:]) 或构建新列表（推导式）。

💡 相关陷阱

循环里创建 lambda/嵌套函数、事后才调用，同样会因为延迟绑定踩坑（全都看到循环变量的最后一个值）。详见 lambda 用法 一节的"lambda 什么时候需要 x=x"。

3. 类属性是可变对象时被共享 · Shared mutable class attribute

4. dataclass 用可变对象当默认值 · Mutable default in dataclass

@dataclass 禁止用 list/dict/set 作字段默认值，在定义类时就抛 ValueError——正是为了防止 #1 / #4 那种"所有实例共享同一个可变对象"。改用 field(default_factory=...)：它是个零参可调用，会为每个实例各建一份新对象。

同理，有默认值的字段必须排在无默认值字段之后（和函数参数一样）。

5. int 与 str 不会隐式转换 · No implicit int/str coercion

和 JS 不同，Python 的 + 在数字和字符串之间不会帮你转类型——直接抛 TypeError。这是很多从 JS/其它语言转过来的候选人会踩的点。

🗣️ Say it in English

“Python is strongly typed at runtime — it won't silently coerce between int and str the way JavaScript does with +. Mixing them raises a TypeError immediately, so I have to be explicit about intent: str(x) if I want concatenation, or int(x) if I want arithmetic.”

6. 线程解决不了 CPU 密集型任务 · Threads don't speed up CPU-bound work

常见面试场景题："这段代码是 CPU 密集型，同事建议用多线程并行化，为什么不行？该怎么做？多线程什么时候才有用？"

  • 为什么线程不行： CPython 有 GIL（全局解释器锁），同一时刻只允许一个线程执行 Python 字节码。CPU 密集任务里线程只是在一个核上来回切换，没有真正并行，还多了上下文切换开销——有时反而更慢。
  • 该用什么： multiprocessing / concurrent.futures.ProcessPoolExecutor——每个进程各有自己的解释器和 GIL，能跑在不同核上实现真并行。也可以把热点循环下沉到会释放 GIL 的 C 扩展 / 向量化库（如 NumPy）。
  • 线程什么时候有用： I/O 密集场景（网络请求、磁盘、数据库查询）——线程大部分时间在等待，等待期间会释放 GIL，让其它线程运行。这正是本节 并发与异步 表格里 threading 适合"IO 密集"的原因。
🗣️ Say it in English

“Threading won't help here because of the GIL — only one thread executes Python bytecode at a time, so for CPU-bound work threads just take turns on a single core with added context-switch overhead, no real speedup. I'd reach for multiprocessing instead: separate processes each get their own interpreter and GIL, so they run truly in parallel across cores. Threads are the right tool when the work is I/O-bound — waiting on network or disk — because the GIL is released during that wait.”
